## Summary

We use AI as a **pipeline of agents with human checkpoints**, not as a single chat. A planning agent turned our design doc and slides into a build spec ([BUILD_PLAN.md](BUILD_PLAN.md)). An execution agent builds the app from that spec one phase at a time. Phases 0–8 are built: scaffold, ingestion, the cited Q&A API, the chat UI, Explain my form, the scenario calculator, quizzes, an evaluation harness, and deploy config and polish. The API is now live on Azure, and a packaged Mac app connects to it. Phase 2's live check passed only after it exposed a schema bug that the 98 unit tests couldn't catch, Phase 3 shipped a UI binding bug that neither its API checks nor our click-through caught, and Phase 4 repeated it: its API passed all 34 live checks while the page showed an error on every box, which only our click-through caught. A separate evaluation session then reviewed both phases, found two chunking problems by measuring the stored data, and fixed them. Phase 1 now loads 1,377 chunks from 9 IRS documents into the vector store. The execution agent has twice found the spec wrong when it checked the real IRS documents, and it flagged both times instead of following the spec blindly. Phase 5 checked its calculator against all 2,062 rows of the official 2025 Tax Table, which the agent extracted from the IRS PDF. A live run then showed its new dollar guardrail rejecting correct explanations, which the unit tests had missed. Phase 7's eval gave the most sobering result so far: TaxWise refused all 12 out-of-scope questions (a plain chatbot refused 1) and got all three 2027 questions right (the chatbot got none), but on 40 ordinary questions it scored **80% correct against the chatbot's 90%**. After the plan, a subagent built the "Upload mine" stretch goal in its own worktree: all 376 tests passed, but the App froze the first time we clicked the upload box, because the sandboxed Mac app lacked the permission to show a file picker. In the same session a page-width bug took three fixes, and the third came only after the agent stopped guessing and measured the page in the running App. For the deploy, we asked the AI to put our API keys inside the App. It explained that anyone who downloaded the app could extract them, so the keys stayed on the server and it added a per-IP usage limit instead. We ran every Azure command ourselves, and the agent read our pasted errors. In the latest session, three background subagents each built one stretch goal on their own branch: a plain-chatbot comparison, voice input and Colorado state tax chat. The main agent merged and deployed their work, and this time ran the Azure deploy and the Qdrant Cloud upload itself. That deploy took live chat down for about 2 minutes, because Qdrant Cloud needed an index the new filter depended on. The agent also launched an out-of-date app build a third time. Of 21 sessions we tagged 10 **partial**. In the first four we overrode the AI's suggested "success". The work was real, but each of those sessions needed us to step in, or the agent changed something we hadn't asked it to.

4. **Evaluation agent.** A separate session reviews finished phases against the plan, so the builder doesn't grade its own work. The first run ([`b1c9df54`](prompt-log.md#2026-11-10--evaluation--claude-code-claude-opus-5-5--cnash03--session-b1c9df54)) reviewed Phases 0 and 1. 5. **Subagents for side work.** After the plan was done, we had the main session hand the "Upload mine" stretch goal to a background subagent in its own git worktree while it fixed a UI bug itself ([`3b05f178`](prompt-log.md#2026-11-17--stretch--claude-code-claude-opus-5-5--cnash03--session-3b05f178)). The agent never had our Azure or Qdrant credentials.
7. **Parallel subagents and an integrator.** For the stretch goals ([`2245e2dc`](prompt-log.md#2026-11-18--stretch--claude-code-claude-opus-5-5--cnash03--session-2245e2dc)) the main agent briefed three background subagents. Each worked in its own git worktree with the same rules: commit only to its own branch, no pushes, green tests, separate ports. When we changed the rules mid-run (credit allowed, then Qdrant Cloud allowed), the main agent passed the change to the running agents. It then re-ran each branch's tests, resolved their conflicts, merged them, deployed and checked the live API.
8. **Logging.** Project hooks record every prompt, tool call, decision and reply, and `/ai-report` turns the records into this page. Subagents' tool calls are logged inside their parent session.

**Divergences from the plan so far:**

- **The evaluator also fixed what it found.** The plan describes an evaluation agent that only reports. In [`b1c9df54`](prompt-log.md#2026-11-10--evaluation--claude-code-claude-opus-5-5--cnash03--session-b1c9df54) we read its findings, picked the two to fix and had the same session fix them. - **Stacked PRs landed on the wrong branch.** The Phase 3 PR was stacked on the open Phase 2 PR. Phase 2 merged first, then Phase 3 was merged into the Phase 2 branch, so it never reached `main` ([`e205fac5`](prompt-log.md#2026-11-10--phase-3--claude-code-claude-opus-5-5--cnash03--session-e205fac5)). The plan's one-PR-per-phase flow assumes each PR targets `main`.
- **The UI check depends on us.** The agent can't click the desktop app, so a human clicks through each UI phase. In Phase 4 that loop took five app builds: we clicked and reported, the agent read the API log and rebuilt, until a screenshot showed the cause.
- **Sessions run out mid-phase.** Phase 4 hit the usage limit at the commit step, so the commit and PR moved to the next session (`9a1333b2`).
- **We now keep a decision record.** BUILD_PLAN doesn't ask for one. Since `9a1333b2`, [DECISIONS.md](../DECISIONS.md) records each design decision with its alternatives and session id. We asked for the older decisions to be added too, against the agent's suggestion to leave them.
- **The golden data changed hands.** BUILD_PLAN says a human copies about 10 Tax Table values by hand. In Phase 5 the agent extracted the whole table from the IRS PDF instead, and the human check became spot-checking rows listed in the PR (DECISIONS #10).
- **The builder ran its own eval.** BUILD_PLAN says the evaluation agent is a separate session. In Phase 7 the agent recommended a smoke run only, leaving the full run to a fresh session; we chose to run everything in the build session. The judge is a different model (Sonnet 5.5), but the gold set, harness and the run come from the same agent.
- **The gold answers were AI-drafted.** BUILD_PLAN §12 says a human writes or approves every gold answer. The agent drafted all 40 from the stored IRS text and we approved them in one step without edits. The 10 judge spot-checks are still open.
- **Deploy is split between us and the agent.** BUILD_PLAN §12 item 6 says a human provisions Azure, Qdrant Cloud and the keys. In Phase 8 the agent built and tested everything that doesn't need those accounts, wrote the commands for us in [DEPLOY.md](DEPLOY.md), and stopped. The Phase 8 PR was merged before deploy. The deploy was done in `24bebf56`: the API is live on Azure, and the packaged Release app answered from it.
- **Mac only for now.** In Phase 8 we chose Mac and Windows builds. In `24bebf56` we turned down the AI's suggested GitHub Actions workflow for Windows and are shipping only the Mac `.dmg` for now.
- **Work beyond the plan.** BUILD_PLAN §11 lists PDF upload as out of scope. We built it anyway after Phase 8 (DECISIONS #17), delegated to a subagent instead of a phase session.
- **The environment wasn't ready.** The agents had to stop for sudo installs, Xcode, Docker and Voyage billing.
- **The agent now runs cloud changes itself.** Until `24bebf56` we ran every Azure and Qdrant Cloud step ourselves. In `2245e2dc` we told the agent to redeploy and load Qdrant Cloud. It deployed with our `az login`, read the Qdrant key from the Azure app settings without printing it, and created a cloud index on its own to end the outage it had caused.
- **The agent merged its own PRs.** BUILD_PLAN ends each phase with a human reviewing and merging. For PRs #14–#16 we told the agent to merge once tests passed, so no human reviewed those diffs before merge. We tested the features in the App afterwards.
- **All three §11 stretch goals were built**, at our request (`2245e2dc`), on top of PDF upload (`3b05f178`). No Colorado questions were added to the eval, because a human has to write the gold answers.

## What we don't let AI decide

- **Tax numbers.** Every constant cites its IRS source line and is hand-checked by a human. Golden test values come from the IRS, never from a model. Since Phase 5 the agent extracts them from the IRS PDF and a human spot-checks them against the page. The LLM never computes a number shown to the student: the dollar guardrail rejects any amount it makes up.
- **Which document edition is the right one.** The ingestion pipeline stops if a PDF's cover year or sha256 doesn't match the manifest, and a human confirms the edition table (BUILD_PLAN §12 item 2).
- **Form-line mappings and glossary definitions.** These are data files that a human reviews, not model output.
- **Secrets and system changes.** API keys live only in user-secrets or backend settings, never in chat or commits. We log in to Claude ourselves (`ant auth login`); the agent only checks `ant auth status`. The logging hook masks keys, and the agent shows stored secrets only as `****`. Billing, sudo installs and pushes to GitHub are done by a human. When we asked to put keys inside the App, the AI pushed back, and they stay in Azure App Service settings. We moved them there with a script we ran ourselves, so they never appeared in the chat.
- **Cloud resources.** We create every Azure and Qdrant Cloud resource ourselves, and the agent changes them only when we tell it to. Until `24bebf56` it only wrote the commands. In `2245e2dc` we let it redeploy the API and load Qdrant Cloud under our `az login`, and it read the stored keys without printing them. It also made one change we hadn't spelled out: it created a cloud index to end the outage its deploy had caused.
- **Gold answers for the eval** (BUILD_PLAN §12 item 5). In Phase 7 we let the agent draft them and approved them in bulk, which is weaker than this rule intends; the judge only scores answers marked `approved`, and the spot-check of 10 verdicts is a human task.
- **Phase approval and outcome tags.** The execution agent stops for approval of each phase plan. We tag outcomes only after testing the result ourselves.

## How this was collected

- **Automatic:** [`.claude/hooks/ai-log.sh`](../.claude/hooks/ai-log.sh) runs on every prompt, tool call, reply and session start or end in Claude Code. It appends to `docs/ai-log/raw/<git-user>/<session>.jsonl`. These files are committed so everyone's report sees the whole team.
- **Missed by the stats script:** `cd2da81e` was reported as already logged because another entry mentioned its id. It got its own entry on 2026-11-17.
- **Backfilled:** `be960576` and `83171a0b` began before the hooks existed and were imported from their Claude Code transcripts with `ai-log.sh backfill`.
- **Corrected:** 9 events from `866029d7` were filed under the wrong author while Xcode was being set up. They were merged back into `cnash03`.
- **Written mid-session:** the `866029d7`, `cc8e27f2`, `b1c9df54`, `14adbac0`, `71ffadc8`, `dacce272`, `3b05f178`, `24bebf56` and `2245e2dc` entries were written by `/ai-report` while those sessions were still running, so each phase's entry could go in with its PR.
- **Redaction:** Anthropic and Voyage keys and `key=`/`token=` values are masked before anything is written. Other identifiers in pasted text, such as our Azure subscription ID in `24bebf56`, are not.
- **Not captured automatically:** AI use outside Claude Code (ChatGPT, Copilot, Claude on the web). `/ai-report` asks about it. So far none has been reported.
