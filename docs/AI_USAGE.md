- **The evaluator also fixed what it found.** The plan describes an evaluation agent that only reports. - **Stacked PRs landed on the wrong branch.** The Phase 3 PR was stacked on the open Phase 2 PR. The plan's one-PR-per-phase flow assumes each PR targets `main`.
- **The UI check depends on us.** The agent can't click the desktop app, so a human clicks through each UI phase. In Phase 4 that loop took five app builds: we clicked and reported, the agent read the API log and rebuilt, until a screenshot showed the cause.
- **Sessions run out mid-phase.** Phase 4 hit the usage limit at the commit step, so the commit and PR moved to the next session (`9a1333b2`).
- **We now keep a decision record.** BUILD_PLAN doesn't ask for one. Since `9a1333b2`, [DECISIONS.md](../DECISIONS.md) records each design decision with its alternatives and session id. We asked for the older decisions to be added too, against the agent's suggestion to leave them.
- **The golden data changed hands.** BUILD_PLAN says a human copies about 10 Tax Table values by hand. In Phase 5 the agent extracted the whole table from the IRS PDF instead, and the human check became spot-checking rows listed in the PR (DECISIONS #10).
- **The environment wasn't ready.** The agents had to stop for sudo installs, Xcode, Docker and Voyage billing.

## Pushing the boundaries

- **An agent executing another agent's spec, and correcting it.** Five phases (0–4) have now been built from BUILD_PLAN.md with one-line prompts. In Phase 1 the execution agent checked the spec against primary sources: it downloaded and probed all 9 IRS PDFs before writing the parser, and found two places where the planning agent's spec was wrong (Rev. Proc. section numbers and stale PDF editions).
- **Grounding the glossary in the stored data.** For Phase 3 the agent pulled every chunk out of Qdrant and wrote each of the 40 glossary definitions from a real TY2025 passage, recording its `chunkId` for human review ([`e205fac5`](prompt-log.md#2026-11-10--phase-3--claude-code-claude-opus-5-5--cnash03--session-e205fac5)).
- **Acceptance as a script, and the agent watching our clicks.** In Phase 4 the agent ran every box on both forms in both modes (34 live requests) and read the sample answers, which led to a prompt fix. While we tested the app it watched the API log with a monitor and told us which request each click produced. That combination narrowed the bug to the app ([`ce6c7853`](prompt-log.md#2026-11-10--phase-4--claude-code-claude-opus-5-5--cnash03--session-ce6c7853)).
- **Testing against the whole official table.** For Phase 5 the agent pulled the text out of the 2025 Form 1040 instructions with PdfPig, parsed all 2,062 Tax Table rows into a CSV, and wrote a test that runs every row in every filing status. It also checked each 2026/2027 constant in BUILD_PLAN against the Rev. Proc. text and turned the 48 base-tax amounts the IRS states into tests. The calculator passed all of them on its first run ([`71ffadc8`](prompt-log.md#2026-11-12--phase-5--claude-code-claude-opus-5-5--cnash03--session-71ffadc8)).
- **A guardrail on the model's numbers.** In the calculator, Claude only explains numbers the code computed. Any dollar amount it writes that isn't in the calculation gets one retry, then is replaced by text built from the numbers.
- **Live checks catch what fakes can't.** Phase 2's 98 tests passed with a fake Claude answerer. The first real call failed on a schema keyword the API doesn't support ([`14adbac0`](prompt-log.md#2026-11-10--phase-2-setup--claude-code-claude-opus-5-5--cnash03--session-14adbac0)).
- **Measuring against real data instead of trusting tests.** The Phase 1 chunker passed its unit tests on the first try, but the agent measured the size distribution on the real IRS PDFs, saw that a quarter of the chunks were tiny, and fixed it over 4 rounds ([`cc8e27f2`](prompt-log.md#2026-11-10--phase-1--claude-code-claude-opus-5-5--cnash03--session-cc8e27f2)).
- **A second agent auditing the first, using data rather than code.** The evaluation session ([`b1c9df54`](prompt-log.md#2026-11-10--evaluation--claude-code-claude-opus-5-5--cnash03--session-b1c9df54)) didn't stop at reading code and re-running tests (all green). It pulled all 1,487 points out of Qdrant and measured them: how many chunks are mostly numbers, and how many section labels are merged. That surfaced two problems the green tests couldn't show. After the fix it measured again: 0 and 0.
- **Acceptance checks as runnable commands.** `--spot-check` turns the plan's manual retrieval checks into a single command with PASS/FAIL output. It confirmed that the TY2027 and TY2026 standard-deduction chunks rank #1 and that the demo question finds Pub 970 p. 5.
- **Parallel agents.** Three Claude sessions worked on one branch at the same time: setup, docs and the build. One session's warning about Voyage rate limits came true in another. The cost was a commit that mixed two sessions' work.
- **Live research into primary sources.** TY2026 and TY2027 numbers come from IRS Rev. Procs published after the model's training cutoff. The Voyage client was written against the live API reference.
- **Documentation tooling as part of the project.** Hooks and a custom skill produce this page, and running it has caught problems in our own process: misfiled log events, and a commit message that didn't match its diff.
- _Planned:_ head-to-head comparisons of Claude Code and Copilot on at least 3 components (BUILD_PLAN §9). **The PDF chunker and the Voyage client were two of the suggested candidates, and both are now built without a comparison.** **The tax calculator is now built without one too**, which leaves the citation chip UI. An eval harness with a no-retrieval baseline is also planned.

## What we don't let AI decide

- **Tax numbers.** Every constant cites its IRS source line and is hand-checked by a human. Golden test values come from the IRS, never from a model. Since Phase 5 the agent extracts them from the IRS PDF and a human spot-checks them against the page. The LLM never computes a number shown to the student: the dollar guardrail rejects any amount it makes up.
- **Which document edition is the right one.** The ingestion pipeline stops if a PDF's cover year or sha256 doesn't match the manifest, and a human confirms the edition table (BUILD_PLAN §12 item 2).
- **Form-line mappings and glossary definitions.** These are data files that a human reviews, not model output.
- **Secrets and system changes.** API keys live only in user-secrets or backend settings, never in chat or commits. We log in to Claude ourselves (`ant auth login`); the agent only checks `ant auth status`. The logging hook masks keys, and the agent shows stored secrets only as `****`. Billing, sudo installs and pushes to GitHub are done by a human.
- **Phase approval and outcome tags.** The execution agent stops for approval of each phase plan. We tag outcomes only after testing the result ourselves.

## How this was collected

- **Automatic:** [`.claude/hooks/ai-log.sh`](../.claude/hooks/ai-log.sh) runs on every prompt, tool call, reply and session start or end in Claude Code. It appends to `docs/ai-log/raw/<git-user>/<session>.jsonl`. These files are committed so everyone's report sees the whole team.
- **Backfilled:** `be960576` and `83171a0b` began before the hooks existed and were imported from their Claude Code transcripts with `ai-log.sh backfill`.
- **Corrected:** 9 events from `866029d7` were filed under the wrong author while Xcode was being set up. They were merged back into `cnash03`.
- **Written mid-session:** the `866029d7`, `cc8e27f2`, `b1c9df54`, `14adbac0` and `71ffadc8` entries were written by `/ai-report` while those sessions were still running, so each phase's entry could go in with its PR.
- **Redaction:** Anthropic and Voyage keys and `key=`/`token=` values are masked before anything is written.
- **Not captured automatically:** AI use outside Claude Code (ChatGPT, Copilot, Claude on the web). `/ai-report` asks about it. So far none has been reported.
